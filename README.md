# WB FBS Automation

Независимая автоматизация Wildberries FBS. Цель: **один заказ → одна поставка → СЦ «Кавказский бульвар» → QR и документы PDF → Telegram**. Проект не затрагивает другие системы Time&Ko.

## Текущая версия: V0.19 — безопасный четырёхстраничный PDF-компоновщик

Подключение WB API подтверждено 10.10.2026: склад продавца `1992848`, целевой СЦ `353731` (тип `sc`, cargoType=1). После 1 октября в проверенной выборке 12 из 12 поставок имели дату и целевой пункт отгрузки. Это **не доказывает**, что публичный API позволяет пропускать дату.

Выполняется при успешном развёртывании в Cloudflare:

- **Каждые 5 минут после активации**: `GET /api/v3/orders/new`, сохранение впервые увиденных ID заказов в приватном Durable Object с защитой от повторного обнаружения.
- **Каждый час после активации**: агрегированная диагностика новых заказов и поставок.
- **Ежедневно в 00:00 UTC**: проверка доступности СЦ `353731`.
- История последних 72 почасовых проверок сохраняется в Durable Object (SQLite).
- **Запись в WB отключена**: поставки не создаются, статусы не меняются, PDF с официальным QR и стикером проверяются в памяти на исторических данных; файлы не отправляются.
- **Однократная проверка документов**: на уже закрытой исторической поставке целевого СЦ Worker проверяет доступность официального QR и стикера заказа. Проверка использует GET для QR/ID и POST для **получения** стикера (не изменение заказа). Содержимое, ID заказов и изображения не сохраняются и не публикуются.
- **Однократный аудит полей заказа**: проверяет, какие поля (артикул, баркод, название, цвет, размер и т. п.) реально возвращаются из Marketplace API. В публичном статусе только имена доступных полей, без значений.
- **Проверка PDF**: преобразует QR ранее закрытой поставки в PDF **58 × 40 мм**. Файл пока не отправляется; PDF-байты отбрасываются после проверки. Генератор находится в `src/pdf.js` и не требует сторонних npm-пакетов.
- **Дополнительный источник полей товара**: расширенный `WB_API_TOKEN` (категории «Маркетплейс» и «Контент») позволяет Worker один раз проверить получение карточки по `nmId` из реального FBS-заказа через `POST https://content-api.wildberries.ru/content/v2/get/cards/list`. Запрос читает данные, не редактирует карточку. В публичный статус попадают только имена доступных полей и совпадение SKU, не сами данные.
- **Telegram**: до привязки бот проверяет новые сообщения через тот же Durable Object Alarm раз в 5 минут; после успешной привязки дополнительный опрос Telegram прекращается. После обновления V0.11 бот **однократно** отправляет тестовое сообщение о работе мониторинга. Повторных тестовых сообщений не будет.

## Активация

После публикации V0.6 (Ready) откройте `https://wb-fbs-automation.andryukov-andrew.workers.dev/status` один раз. В ответе должно быть `scheduler: durable_object_alarm` и `alarm.scheduled: true`. Примерно через минуту начнётся первый опрос, затем каждые пять минут. Если версия на `/health` старая, дождитесь деплоя.

## Адреса Worker

- [`/health`](https://wb-fbs-automation.andryukov-andrew.workers.dev/health) — версия и режим; не проверяет WB API.
- [`/status`](https://wb-fbs-automation.andryukov-andrew.workers.dev/status) — публичное состояние планировщика без ID заказов и токенов.
- `/diagnostics` — защищённая сводка WB API.
- `/diagnostics/shipping-dates` — защищённая историческая проверка дат.
- `/diagnostics/history` — защищённая история почасовых проверок.
- `/diagnostics/order-monitor` — защищённые агрегированные счётчики мониторинга заказов.

Защищённые маршруты требуют заголовка `X-Admin-Key`; **не передавать ключ в URL или чат**.

## Подключение нового Telegram-бота

1. В Cloudflare Worker → Settings → Variables and Secrets добавьте два значения типа **Secret**:
   - `TELEGRAM_BOT_TOKEN` — HTTP API Token от @BotFather;
   - `TELEGRAM_PAIR_CODE` — придуманный отдельно случайный код длиной **не менее 10** символов, только латинские буквы, цифры, дефис или подчёркивание (рекомендуется 16+).
2. Дождитесь успешного деплоя V0.11. В личном чате с созданным ботом отправьте **`/start ВАШ_КОД`**. Не отправляйте токен или код в GitHub или ChatGPT.
3. Через 5–6 минут бот должен прислать подтверждение. В `/status` будет `telegram: "connected"`. Привязка выполняется **один раз**, без ручного поиска Chat ID, и хранится в приватном Durable Object.
4. До подключения обоих секретов мониторинг WB продолжает работать, Telegram не опрашивается.

Привязка не запускает создание поставок и не отправляет реальные документы. После деплоя V0.11 в `/status` появится `telegramTest: "not_sent" | "attempted" | "sent" | "failed" | "unconfirmed"`. Проверка отправки запускается автоматически на следующем Alarm и **не повторяется** при неопределённом ответе Telegram, чтобы избежать дублей. Если бот уже использует webhook или другой `getUpdates` клиент, привязка через опрос может не сработать.

## Секреты Cloudflare

Cloudflare Worker → Settings → Variables and Secrets, тип **Secret**:

- `WB_API_TOKEN` — токен WB категории Marketplace.
- `ADMIN_KEY` — независимый случайный ключ для защищённой диагностики.
- `TELEGRAM_BOT_TOKEN` — токен нового Telegram-бота.
- `TELEGRAM_PAIR_CODE` — одноразовый код привязки получателя.
- Отдельный `WB_CONTENT_TOKEN` **не нужен**: один `WB_API_TOKEN` должен иметь разрешения «Маркетплейс» и «Контент».

Значения секретов не коммитить в GitHub и не публиковать в логах.

## Инфраструктура

- GitHub `main` → Cloudflare Builds → `npx wrangler deploy`.
- `wrangler.jsonc`: **без Cron Trigger**, SQLite Durable Object `DIAG_HISTORY`. Запуск планируется через `ctx.storage.setAlarm()` в Durable Object.
- После успешного деплоя **один раз откройте `/status`**, чтобы включить Durable Object Alarm; далее он сам перепланируется каждые пять минут. **Коммит в GitHub не доказывает успешный деплой**; проверьте Ready и версию `/health`.

## Экономия лимитов Cloudflare

- Ноль новых Cron Triggers: один Durable Object Alarm каждые пять минут (около 288 запусков в сутки).
- Почасовая диагностика выполняется при первом срабатывании Alarm в каждом UTC-часе.
- Ежедневная проверка целевого СЦ выполняется при первой почасовой диагностике после 00:00 UTC.
- Режим READ_ONLY не создаёт поставки и не отправляет сообщения.
- Лимиты Cloudflare Free являются общими для всех Workers аккаунта; фактическое потребление остальных проектов здесь не видно.
- Для мгновенной обработки реальных заказов потребуется отдельно выбрать подходящую частоту/механизм уведомления с учётом квот.
- Удаление `triggers` из конфигурации не удаляет старые Cron Triggers, если они ранее были зарегистрированы; для этого требуется отдельная проверка Cloudflare Triggers. `scheduled()` сейчас намеренно ничего не делает.

## Форматы эталонных PDF (по образцам от 09.10.2026)

- `Qr поставки.pdf`: 1 страница, **58 × 40 мм**, QR поставки WB, идентификатор WB-GI, количество и пункт отгрузки.
- `Стикеры поставки.pdf`: **4 отдельные страницы по 40 × 30 мм**:
  1. Обложка поставки с датой, названием и количеством.
  2. Информация о товаре (наименование, цвет, размер, артикулы, баркод).
  3. Товарный штрихкод и данные товара.
  4. **Официальный стикер WB** (не генерировать произвольный QR вместо официального).
- Получение: `GET /api/v3/supplies/{supplyId}/barcode?type=png` и `POST /api/v3/orders/stickers?type=png&width=40&height=30` (запрос на чтение изображения).
- В `/status` поле `documentProbe` показывает результат однократной проверки источников на исторической поставке, **без раскрытия ID/изображений**.
- `orderMetadataProbe` — наличие полей для страниц 1–3 второго PDF.
- `pdfEngineProbe` — результат создания настоящего PDF из официального QR (ожидаем `state: complete`, `page: 58x40mm`).
- `contentCardProbe` — проверка карточки по `nmId`; без секрета будет `state: awaiting_content_token`, после проверки ожидаем `state: complete` и `matchByNmId: true`.

## Правила дальнейшей автоматизации

1. Сохранять связь заказа и поставки в Durable Object; не создавать дубликаты при сбоях или повторном опросе.
2. Отправлять документы только для подтверждённого СЦ `353731`.
3. Не придумывать дату отгрузки. Перед автоматическим `deliver` установить, как реальный кабинет WB заполняет обязательные параметры, и проверить официальный API.
4. Проверить настоящие WB-стикеры, QR и четыре **разные** страницы второго PDF на тестовом заказе.
5. Отправлять оба PDF в Telegram автоматически, без подтверждений и ввода даты. Токен бота и chat ID хранить отдельно от GitHub.
6. Любые операции записи включать только после безопасной проверки сценария.

## V0.18–V0.19 — безопасные этапы

- Публичный `/status.pendingOrderProbe.state=awaiting_sticker_eligibility` означает, что WB ответил HTTP 200 с пустым массивом стикеров. Это **не доказательство** причины; исходные данные сохранены, статус заказа не меняется.
- Однократно выбирается **закрытая историческая** поставка целевого СЦ `353731`. Только если в ней ровно один заказ и официальный стикер подтверждён по ID, генерируется **одна страница PDF 40×30 мм**. Результат проверки — `/status.historicalStickerPdfProbe`.
- PDF создаётся только в памяти и уничтожается. Никакие идентификаторы, изображения, карточки товаров, PDF и данные покупателей не сохраняются и не выдаются через публичный статус.
- **V0.19:** функция `fourPagePngPdf` в `src/pdf.js` собирает четыре PNG в один PDF с четырьмя страницами **40×30 мм**. Входной порядок: обложка, информация о товаре, товарный штрихкод, официальный стикер WB. Это компоновщик, **не генератор содержимого** первых трёх страниц.
- **V0.19:** однократная проверка `/status.fourPageCompositorProbe` использует исключительно четыре синтетические PNG. Она проверяет структуру PDF, число страниц и размеры, **не** подтверждает правильность реальных этикеток. Никаких новых запросов к WB для этой проверки нет.
- Следующий шаг — надёжная отрисовка первых трёх страниц с кириллицей, проверка EAN-13, сопоставление с одним и тем же заказом и визуальное тестирование. До этого нельзя считать комплект пригодным к печати.
- До проверки даты и способа отгрузки проект остаётся в `READ_ONLY`; создание поставок и отправка PDF в Telegram отключены.
