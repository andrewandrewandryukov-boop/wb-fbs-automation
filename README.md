# WB FBS Automation

Независимая автоматизация Wildberries FBS. Цель: **один заказ → одна поставка → СЦ «Кавказский бульвар» → QR и документы PDF → Telegram**. Проект не затрагивает другие системы Time&Ko.

## Текущая версия: V0.8 — безопасная привязка и проверка отправки Telegram

Подключение WB API подтверждено 10.10.2026: склад продавца `1992848`, целевой СЦ `353731` (тип `sc`, cargoType=1). После 1 октября в проверенной выборке 12 из 12 поставок имели дату и целевой пункт отгрузки. Это **не доказывает**, что публичный API позволяет пропускать дату.

Выполняется при успешном развёртывании в Cloudflare:

- **Каждые 5 минут после активации**: `GET /api/v3/orders/new`, сохранение впервые увиденных ID заказов в приватном Durable Object с защитой от повторного обнаружения.
- **Каждый час после активации**: агрегированная диагностика новых заказов и поставок.
- **Ежедневно в 00:00 UTC**: проверка доступности СЦ `353731`.
- История последних 72 почасовых проверок сохраняется в Durable Object (SQLite).
- **Запись в WB отключена**: поставки не создаются, статусы не меняются, QR/PDF ещё не реализованы.
- **Telegram**: до привязки бот проверяет новые сообщения через тот же Durable Object Alarm раз в 5 минут; после успешной привязки дополнительный опрос Telegram прекращается. После обновления V0.8 бот **однократно** отправляет тестовое сообщение о работе мониторинга. Повторных тестовых сообщений не будет.

## Активация

После публикации V0.6 (Ready) откройте `https://wb-fbs-automation.andryukov-andrew.workers.dev/status` один раз. В ответе должно быть `scheduler: durable_object_alarm` и `alarm.scheduled: true`. Примерно через минуту начнётся первый опрос, затем каждые пять минут. Если версия на `/health` старая, дождитесь деплоя.

## Адреса Worker

- [`/health`](https://wb-fbs-automation.andryukov-andrew.workers.dev/health) — версия и режим; не проверяет WB API.
- [`/status`](https://wb-fbs-automation.andryukov-andrew.workers.dev/status) — публичное состояние планировщика без ID заказов и токенов.
- `/diagnostics` — защищённая сводка WB API.
- `/diagnostics/shipping-dates` — защищённая историческая проверка дат.
- `/diagnostics/history` — защищённая история почасовых проверок.
- `/diagnostics/order-monitor` — защищённые агрегированные счётчики мониторинга заказов.

Защищённые маршруты требуют заголовка `X-Admin-Key`; **не передавать ключ в URL или чат**.

## Подключение нового Telegram-бота

1. В Cloudflare Worker → Settings → Variables and Secrets добавьте два значения типа **Secret**:
   - `TELEGRAM_BOT_TOKEN` — HTTP API Token от @BotFather;
   - `TELEGRAM_PAIR_CODE` — придуманный отдельно случайный код длиной **не менее 10** символов, только латинские буквы, цифры, дефис или подчёркивание (рекомендуется 16+).
2. Дождитесь успешного деплоя V0.8. В личном чате с созданным ботом отправьте **`/start ВАШ_КОД`**. Не отправляйте токен или код в GitHub или ChatGPT.
3. Через 5–6 минут бот должен прислать подтверждение. В `/status` будет `telegram: "connected"`. Привязка выполняется **один раз**, без ручного поиска Chat ID, и хранится в приватном Durable Object.
4. До подключения обоих секретов мониторинг WB продолжает работать, Telegram не опрашивается.

Привязка не запускает создание поставок и не отправляет реальные документы. После деплоя V0.8 в `/status` появится `telegramTest: "not_sent" | "attempted" | "sent" | "failed" | "unconfirmed"`. Проверка отправки запускается автоматически на следующем Alarm и **не повторяется** при неопределённом ответе Telegram, чтобы избежать дублей. Если бот уже использует webhook или другой `getUpdates` клиент, привязка через опрос может не сработать.

## Секреты Cloudflare

Cloudflare Worker → Settings → Variables and Secrets, тип **Secret**:

- `WB_API_TOKEN` — токен WB категории Marketplace.
- `ADMIN_KEY` — независимый случайный ключ для защищённой диагностики.
- `TELEGRAM_BOT_TOKEN` — токен нового Telegram-бота.
- `TELEGRAM_PAIR_CODE` — одноразовый код привязки получателя.

Значения секретов не коммитить в GitHub и не публиковать в логах.

## Инфраструктура

- GitHub `main` → Cloudflare Builds → `npx wrangler deploy`.
- `wrangler.jsonc`: **без Cron Trigger**, SQLite Durable Object `DIAG_HISTORY`. Запуск планируется через `ctx.storage.setAlarm()` в Durable Object.
- После успешного деплоя **один раз откройте `/status`**, чтобы включить Durable Object Alarm; далее он сам перепланируется каждые пять минут. **Коммит в GitHub не доказывает успешный деплой**; проверьте Ready и версию `/health`.

## Экономия лимитов Cloudflare

- Ноль новых Cron Triggers: один Durable Object Alarm каждые пять минут (около 288 запусков в сутки).
- Почасовая диагностика выполняется при первом срабатывании Alarm в каждом UTC-часе.
- Ежедневная проверка целевого СЦ выполняется при первой почасовой диагностике после 00:00 UTC.
- Режим READ_ONLY не создаёт поставки и не отправляет сообщения.
- Лимиты Cloudflare Free являются общими для всех Workers аккаунта; фактическое потребление остальных проектов здесь не видно.
- Для мгновенной обработки реальных заказов потребуется отдельно выбрать подходящую частоту/механизм уведомления с учётом квот.
- Удаление `triggers` из конфигурации не удаляет старые Cron Triggers, если они ранее были зарегистрированы; для этого требуется отдельная проверка Cloudflare Triggers. `scheduled()` сейчас намеренно ничего не делает.

## Правила дальнейшей автоматизации

1. Сохранять связь заказа и поставки в Durable Object; не создавать дубликаты при сбоях или повторном опросе.
2. Отправлять документы только для подтверждённого СЦ `353731`.
3. Не придумывать дату отгрузки. Перед автоматическим `deliver` установить, как реальный кабинет WB заполняет обязательные параметры, и проверить официальный API.
4. Проверить настоящие WB-стикеры, QR и четыре **разные** страницы второго PDF на тестовом заказе.
5. Отправлять оба PDF в Telegram автоматически, без подтверждений и ввода даты. Токен бота и chat ID хранить отдельно от GitHub.
6. Любые операции записи включать только после безопасной проверки сценария.

## Следующий этап

После успешной привязки Telegram и одноразовой проверки исходящей отправки реализовать подготовку документов и проверить последовательность операций создания поставки. До проверки даты и способа отгрузки проект остаётся в `READ_ONLY`.
