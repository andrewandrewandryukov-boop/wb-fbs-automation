# FBS: как получать оригинальные PDF WB (исследование 2026-10-11)

## Подтверждено официальными источниками
- WB Partners: https://seller.wildberries.ru/instructions/ru/am/material/stickers-for-marking-orders-fbs-model
  Кабинет формирует четыре типа стикеров: «Данные о поставке», «Артикул для подбора», «Стикер баркода», «Стикер WB». Через «Печать стикеров» появляется предпросмотр готового PDF.
- WB API: https://dev.wildberries.ru/en/docs/openapi/orders-fbs?locale=ru
  POST /api/v3/orders/stickers возвращает ТОЛЬКО официальный стикер WB в SVG/ZPL/PNG, не полный PDF четырёх типов. Только для заказов в confirm/complete. 40×30 поддерживается для этого стикера.
- WB Knowledge Base: https://dev.wildberries.ru/knowledge-base/articles/019d49a4-0771-7571-aea9-11d5b597f34c
  Описаны методы получения официальных стикеров и сценарий поставок.

## Новое подтверждение по ОРИГИНАЛЬНЫМ файлам пользователя (11 октября)
Проведён **локальный анализ байтов оригинальных**, а не самостоятельно сгенерированных PDF:
- `Стикеры поставки.pdf`: **4 страницы**, каждая MediaBox **113.39 × 85.04 pt** (40 × 30 мм); PDF **1.3**, Producer **FPDF 1.7**; CreationDate **2026-10-09 14:50:48** (часовой пояс в PDF не указан).
- `Qr поставки.pdf`: **1 страница**, MediaBox **164.41 × 113.39 pt** (58 × 40 мм); PDF **1.3**, Producer **FPDF 1.7**; CreationDate **2026-10-09 14:51:33**.
- В **обоих** файлах встроены два CID TrueType шрифта: **`utf8arial_bold`** и **`utf8arial_reg`**. Не передавать файлы шрифтов, использовать только метаданные.
- Текст первых трёх стикеров — **реальный извлекаемый PDF-текст**, а не сплошные растровые изображения. Страница 4 содержит официальную WB графику и текст. Внутри также имеются изображения (штрихкоды и QR).
- Значение **FPDF 1.7** указывает на семейство FPDF-генераторов; оно **не доказывает**, что PDF генерируется сервером, и **не доказывает** язык реализации (PHP/Python). Но делает гипотезу о jsPDF/pdfmake как непосредственном создателе эталона менее вероятной.
- Структура и шрифты двух документов совпадают по именам, поэтому разумная рабочая гипотеза — **один генератор для QR и комплекта стикеров**. Нужна проверка сетевого ответа, чтобы установить точный источник.

### Что меняет это открытие
Исследовать не произвольный PDF-рендерер, а источник PDF с Producer **FPDF 1.7** и конкретные API/шаблоны. Не копировать исходные данные/QR пользователя в репозиторий и не заменять официальную печать самодельным макетом. Не обещать идентичности до сравнения с эталоном.

## Пока НЕ подтверждено
- Публичный API для получения исходного PDF из четырёх страниц.
- Выдаёт ли кабинет PDF непосредственно с сервера или собирает его JavaScript в браузере (Blob/pdfmake/jsPDF и т.п.).
- Возможно ли получить идентичный PDF с Cloudflare Worker без интерактивной сессии кабинета.
- Как безопасно воспроизвести формирование PDF после создания поставки и как решить дату отгрузки без выдумывания даты.

## Следующий технический эксперимент — без записи в WB
1. В кабинете WB открыть **старую закрытую поставку**, если интерфейс позволяет её печать; иначе уже существующую поставку без изменения статуса.
2. В Chrome DevTools → Network включить Preserve log; фильтр Fetch/XHR и отдельно All.
3. Нажать «Печать стикеров», отметить все четыре вида, нажать «Распечатать».
4. Установить, возникает ли ответ application/pdf, JSON/base64, blob: URL или JS-генерация на клиенте; записать только домен, путь (без query), HTTP method, content-type и общую схему ответа.
5. **Нельзя пересылать полный HAR/Copy as cURL**, заголовки Authorization/Cookie, API-токены, персональные данные, URL с подписанными параметрами. Нельзя повторять запросы, пока не проверено, что это чистое чтение.
6. При серверной выдаче: отдельно проверить, требует ли запрос cookie-сессию или допускает штатный API token. При клиентской генерации: изучить точные исходные шаблоны/стили, без предположения, что достаточно официального API.
7. Сравнить оригинальный PDF из браузера с эталоном по количеству страниц, MediaBox, тексту, штрихкодам и ориентации.

## Решение
Не пытаться подменять оригинальные PDF приближёнными макетами. Не включать WB write-операции, автоматическую доставку документов и хранение авторизационных данных кабинета, пока эксперимент не завершён. Существующий режим READ_ONLY и мониторинг сохранить. Текущий четырёхстраничный компоновщик — только прототип и не подтверждает совпадение с WB.
